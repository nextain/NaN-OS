# 적대리뷰 기록

리뷰어에게 코드·테스트·취지와 사용자의 원본 요청을 함께 넘기고, 작성자의 프레임과
결론 자체를 반박해도 된다고 명시한 뒤 받은 결과다. 통과할 때까지 고치고 다시 돌린다.

| 회차 | 판정 | 지적 수 |
|---|---|---|
| 1회차 | NOT_CLEAN | 8 |
| 2회차 | NOT_CLEAN | 10 |
| 3회차 | NOT_CLEAN | 9 |
| 4회차 | NOT_CLEAN | 7 |
| 5회차 | NOT_CLEAN | 4 |
| 6회차 | NOT_CLEAN | 5 |
| 7회차 | NOT_CLEAN | 6 |
| 8회차 | NOT_CLEAN | 4 |
| 9회차 | NOT_CLEAN | 2 |
| 10회차 | NOT_CLEAN | 3 |
| 11회차 | NOT_CLEAN | 4 |
| 12회차 | NOT_CLEAN | 2 |

연속 두 번 CLEAN 이 목표다. 아직 도달하지 않았으면 이 표가 그 사실을 말한다 —
통과했다고 적어 두고 넘어가지 않기 위해 판정을 그대로 남긴다.
## 회차별로 무엇이 드러났나

**1회차** — 영수증이 파일 단위 종료 코드로 생기고 있었다. 실행기가 뜨기만 하면 증거가 됐고,
매핑된 파일의 무관한 테스트가 통과해도 시나리오가 증명된 것으로 셈됐다. 라이브 게이트는
"결과가 나왔나"만 보고 있어서 거절이 섞여도 종료 코드가 0 이었다. 기준선 0 과 무한대 임계는
게이트가 아니었다.

**2회차** — 작성자가 넣은 실제 보안 결함이 나왔다. 작업자 어댑터가 `sh -c` 에 작업자 식별자를
문자열로 끼워 넣어, 식별자에 셸 메타문자가 오면 소유 경로 검사를 통과하고도 그 밖에서 명령이
돌 수 있었다. 이 슬라이스가 코어에 요구하는 규칙(구조화 명령·셸 조립 금지)을 정작 검증
하네스가 어기고 있었다. 안전 관측도 자기충족이었다 — 누출 목록이 늘 빈 상수였다.

**3회차** — 증거 등급이 경로 허용목록과 작성자가 적은 이름으로만 정해지고 있었다. 같은 실행을
native 라고도 worker 라고도 적을 수 있으니 벤치가 자기 설정을 검증하는 구조였다. 감사가
실패해도 예외를 삼켜 "확인 불능"이 "깨끗함"으로 읽혔다.

## 조건을 켤 때마다 점수가 떨어졌다

| 시점 | 수용 | 무엇을 켰나 |
|---|---|---|
| 1회차 전 | 34/34 | — |
| 케이스 선택자 | 9/34 | 종료 코드 대신 시나리오 케이스가 실제로 통과했는지 |
| 선택자 도출 교정 | 34/35 | 문서의 FR 식별자에서 기계적으로 도출 |
| 관측 증명서 | 14/35 | 실환경 등급은 무엇을 만졌는지 증명서를 남겨야 |

떨어질 때마다 앞의 수치가 무엇에 기대 있었는지 드러났다. 숫자가 회복되는 것은 조건을
낮춰서가 아니라 적용 단위를 바로잡아서여야 한다 — 그 구분이 이 기록의 목적이다.

**4회차** — 실행 어댑터가 `command.executable` 을 무시하고 args 만 돌렸다. 대상 코드가 엉뚱한
실행 파일을 넘겨도 통과했다는 뜻이다. 픽스처는 경계 검사 없이 진입점을 써서 손상된 spec 이
루트 밖 파일을 덮어쓸 수 있었다. argv 구조 주장도 사실과 달랐다 — Herdr 의 `pane run` 은
argv 가 아니라 한 줄을 받으므로 그 경계에서 구조가 깨지는데 "배열 그대로 넘긴다"고 적어
두었다. 보고서가 원시 영수증을 남기지 않아 저장소만으로는 무엇이 돌았는지 확인할 수 없었다.

**5회차** — 요구사항을 성공한 단계에서만 모으고 있었다. 어떤 FR 을 담당한 명령이 실패하면
그 FR 이 확인 목록에서 사라지고 다른 단계의 영수증만으로 시나리오가 수용됐다. 실패가 증명을
약화시키는 게 아니라 요구를 줄이고 있었던 셈이다. 유예도 작성자 상수 하나로 성립해서,
아무 시나리오나 넣으면 게이트가 초록불이 됐다.

## 작성자가 스스로 저지른 것

라벨을 다는 작업이 추적을 만드는 일에서 **벤치를 통과시키려고 이름을 맞추는 일**로 미끄러진
적이 있다. `FR-ENV-LIVE.4`(터미널 입력 권한)를 그 요구사항과 무관한 origin 확인 테스트에
붙였다가 되돌렸다. 이름만 맞으면 벤치는 통과시키므로, 라벨 부착은 언제든 추적이 아니라
추적처럼 보이는 것을 만들 수 있다. 이 위험 자체를 이후 리뷰의 원자로 넣었다.

편집이 실제로 붙었는지 확인하지 않고 넘어간 적도 두 번 있다. 한 번은 들여쓰기 불일치로
치환이 빗나갔고, 한 번은 옛 코드가 남아 시나리오의 영수증을 통째로 무르고 있었다. 이후로는
치환에 개수 단언을 걸었다.

**8회차** — 주의(watch/unwatch) 기능을 넣은 뒤의 첫 리뷰다. 네 가지가 나왔고 전부 실제
결함이었다. 관측이 끊겨도 마지막 보고서가 남아 이미 닫힌 터미널 이름이 계속 뇌로 갔다.
지켜보기를 끄는 정책이 없어서, 모델이 unwatch 를 안 부르면 세션 내내 목록이 실렸다 —
사용자가 지적한 바로 그 상태로 되돌아가는 길이 열려 있었다. 설정은 config 필드만 있고
화면이 없어 "사용자에게 옵셔널하게"의 절반만 한 셈이었다. 그리고 일부러 숨긴 개수와
상한에 잘린 개수를 같은 필드로 뭉갰다 — wire 를 안 바꾸려던 작성자의 편의였는데,
받는 쪽에서 둘은 할 수 있는 일이 다르다.

리뷰어가 짚은 것 중 가장 뼈아픈 것은 **테스트가 다른 것을 재고 있었다**는 지적이다.
성공→성공 전이만 재는 신선도 테스트는 "관측이 끊긴 뒤"라는 실패 양식을 원리적으로
잡을 수 없었고, 서로 다른 초기 설정으로 앱을 새로 부팅해 비교하는 설정 테스트는
실행 중 변경이 안 먹는 결함을 가리고 있었다.

**9회차** — 주의 수명주기를 gRPC 대화 경로에만 걸어 두었다는 것이 드러났다. 음성 도구
호출은 같은 dispatch 를 타므로 음성 중에도 지켜보기를 켤 수 있는데, 거기서는 예산이 줄지
않았다. "켜 둔 채 잊는 것을 막는다"는 규칙이 지원되는 대화 경로 하나에서 성립하지 않았다.

**10회차** — 9회차 수정이 만든 새 구멍이 나왔다. 음성에서 `watch` 를 부르면 "다음 요청부터
목록이 실린다"고 답하는데, 음성 요청에는 표면 세그먼트가 애초에 실리지 않는다. 이 슬라이스
전체가 "거절을 성공으로 바꾸지 않는다"를 원칙으로 세워 놓고, 정작 도구가 못 하는 것을
한다고 말하고 있었다. 그리고 그 지적의 근거가 **"작성자의 테스트가 카운터 공유만 재고
있다"**였다 — 아홉 회차 내내 나온 그 양식이, 그것을 막겠다고 만든 테스트에서 또 나왔다.

중단으로 끝난 음성 턴이 예산을 우회하는 것도 함께 나왔다. 이것은 작성자가 리뷰 전에
스스로 짚은 것과 같아, 드물게 양쪽이 독립적으로 같은 자리를 짚은 경우다.

세 번째는 작아 보이지만 성질이 같다. 작성자가 `listWithheld: false` 를 모든 요청에 싣고
주석에 "wire 형태가 흔들리지 않게 한다"고 적어 두었는데, 그것은 작성자의 편의였고
사용자가 지적한 것은 요청마다 붙는 비용이었다. 비용을 줄이려던 작업이 비용을 더하고
있었다.

**11회차** — 작성자가 세운 규칙을 작성자의 코드가 어기고 있었다. 성공 판정을 결과 문자열의
접두사 두 개로 하고 있었는데, 그 뒤에 새 사유(`무시됨:`)를 추가하면서 판정식은 고치지
않았다. 설정이 이겨 상태가 안 바뀐 경우와 관측 자체가 실패한 경우가 뇌에는 성공으로
보고되고 있었다 — FR-ENV-LIVE.5 가 금지하는 바로 그 일이다. 판정을 실행기가 내도록
구조를 바꿨다. 접두사로 되짚는 방식은 새 사유가 생길 때마다 조용히 샌다.

경로 표시도 뒤집었다. 작성자가 "이 호출은 음성이다"를 호출부더러 단언하게 만들어서,
표시하지 않은 경로는 전부 "요청을 조립한다"가 됐다. 실측해 보니 능동 발화 레인은 뇌가
밀어 주는 것이라 셸이 요청을 조립조차 하지 않는다. 기본값을 겸손한 쪽으로 뒤집었다 —
모르는 경로가 생기면 거짓 약속이 아니라 사실보다 조심스러운 답이 나가야 한다.

네 번째 지적이 이 에픽의 성격을 드러낸다. "나이아가 스스로 판단한다"는 아직 증명되지
않았다. 테스트는 전부 watch·unwatch 인자를 미리 넣는다 — 배선을 재는 것이지 판단을 재는
것이 아니다. `UC-ENV-ATTENTION-POLICY` 로 따로 선언하고 미검증으로 남겼다. 실제 모델을
여러 대화 상황에 놓고 재야 하고, 그것은 비용과 자격증명이 드는 사람 결정이다.

**12회차** — 작성자가 "소유권"이라고 부른 것이 소유권이 아니었다. 통화 시작 시점의 참·거짓
하나로 판정하고 있어서, 통화 도중 다른 경로가 켠 지켜보기도 그 통화가 껐고, 늦게 도착한
옛 세션의 종료가 새 세션의 것을 지울 수 있었다. 켠 주인의 표를 붙이고 그 표가 붙은 것만
끄도록 바꿨다.

두 번째는 부분 성공이었다. `watch` 가 먼저 켜고 관측이 실패하면 `ok:false` 를 냈는데
켜진 것은 그대로 남았다 — 실패라고 말하면서 노출 상태만 바꿔 두는 셈이고, 뒤에 환경이
살아나면 성공한 watch 없이 이름이 실린다. 관측을 먼저 하고 성공했을 때만 켠다.

반영 과정에서 작성자가 또 다른 것을 재고 있었다. 소유권 경쟁을 재려고 만든 실 UI
시나리오의 마지막 단언이 **새 요청이 아니라 옛 요청**을 읽고 있었다. 헬퍼가 그것을 숨기지
못하게 고치자 진짜 사실이 드러났다 — 통화가 살아 있는 동안에는 텍스트 전송 자체가 되지
않아, 그 순서는 실제로 일어날 수 없었다. 가짜 테스트를 남기지 않고 지운 뒤, 왜 못 재는지와
소유권 판정을 어디가 드는지를 스펙에 적었다.

## 이 기록의 목적

점수가 올라간 것이 조건을 낮춰서인지 적용 단위를 바로잡아서인지 구분되도록 남긴다.
판정은 고치지 않는다 — NOT_CLEAN 이었던 회차는 NOT_CLEAN 으로 남는다.

## 환경을 재지 않고 짐작해서 생긴 것

여덟 회차에 걸쳐 나온 지적 중 여럿은 같은 뿌리였다 — 규칙을 환경에서 재지 않고
머릿속 모양으로 썼다.

| 짐작한 것 | 실제 |
|---|---|
| 픽스처 진입점 형식 | 파서는 백틱 안 경로만 읽는다 |
| 프로젝트 선언 경로 | 루트 기준으로 해석된다 |
| Herdr `pane run` 이 argv 를 받는다 | 한 줄을 받는다 |
| 셸 워크스페이스 테스트를 루트에서 실행 가능 | 그 워크스페이스 설정이 필요하다 |
| Herdr 식별자가 `p<숫자>` | `p<영숫자>` (`p1A`·`pM`) |
| `off` 면 herdr 호출이 0일 것 | 워크스페이스 앱과 터미널 위젯이 같은 명령을 쓴다 |
| 스냅샷 갱신이 비싸다 | 10ms (실측) — LLM 호출 앞에서는 무시할 수준 |
| 손잡이 사망 테스트가 끊김을 잰다 | 대상이 에이전트 없는 터미널이라 늘 거절됐다(공허) |
| 변이 탐침 한 번이면 충분하다 | 소스 변경 직후 첫 실행은 dev 서버의 옛 모듈을 쓴다 |
| 벤치를 백그라운드로 돌려도 된다 | 그동안 변이 탐침을 하면 결과가 오염된다 |
| 음성 턴은 늘 `response.done` 으로 끝난다 | 중단·barge-in 은 `onInterrupted` 만 부른다 |
| 음성 버튼으로 끄면 `onDisconnect` 가 온다 | 사용자 중지는 부르지 않는다(테스트가 공허했다) |
| 계열은 배열 순서로 찾으면 된다 | 접두사를 확장한 시나리오가 남의 등급을 물려받는다 |
| 통화 중에도 텍스트를 보낼 수 있다 | 통화가 살아 있으면 chat_request 자체가 안 나간다 |
| 마지막 요청을 읽으면 그 턴의 것이다 | 턴이 안 나갔으면 옛 요청을 읽고 통과한다 |
| 변이 실행이 빈 출력이면 통과다 | 빈 결과는 증거가 아니다 — 실행 자체가 실패한 것 |

Herdr 식별자 건은 위조를 막으려던 규칙이 오히려 **진짜 자원을 거절**하게 만들었다.
규칙을 실측 없이 쓰면 막아야 할 것은 못 막고 통과해야 할 것을 막는다.

마지막 줄은 성질이 다르다. 나머지가 "몰라서 틀린 것"이라면 그것은 **테스트가 통과하는
바람에 틀린 줄 몰랐던 것**이다. 초록불이 근거가 되지 못하는 경우이고, 그래서 이 저장소는
새 테스트마다 변이 탐침을 요구한다 — 고친 자리를 되돌렸을 때 그 테스트가 실제로
깨지는지 보지 않으면, 통과는 아무것도 증명하지 않는다.

전부 "한 번 돌려 보면 알았을 것"들이고, 벤치를 만드는 작업이었는데 그 작업 동안
같은 실수를 반복했다.
