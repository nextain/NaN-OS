# 회귀 실행 기록

기계마다 자기 몫의 실기 회귀를 돌리고 결과를 이 디렉터리에 남긴다.

```
node scripts/run-regression.mjs --machine=<이름> --tier=deterministic_ci[,credentialed_live,native_local]
```

남는 파일 하나가 그 기계의 한 번 실행이다. 담기는 것은 다음과 같다.

| 필드 | 뜻 |
|---|---|
| `planned` | 이 기계가 맡기로 한 스펙. **관측이 아니라 계획이다** |
| `executed` | 실제로 끝까지 돈 스펙. 완결성 판정은 이것만 센다 |
| `groups` | wdio 설정별 결과. 한 설정이 실패해도 다른 설정의 결과는 남는다 |
| `envMissingBeforeRun` | 실행 전에 환경이 없어 건너뛸 것으로 예측한 스펙 |
| `status` | `passed` / `failed` / `prerequisites-missing` |

`planned` 와 `executed` 를 나눈 이유가 있다. 예전에는 계획을 그대로 배정으로
적었고 완결성 게이트가 그것을 덮인 것으로 셌다. 그러면 wdio 가 시작하자마자
죽어도 기록에는 전부 덮였다고 남는다. **손으로 기록을 만들 때 `executed` 를
빠뜨리면 그 기계의 몫은 전부 미실행으로 집계된다.**

### 돌리기 전에 알아야 할 것

**모든 스펙이 짝 naia-agent 체크아웃을 요구한다.** 전용 설정만 그렇다고 오래
믿었는데, 기본 설정(`e2e-tauri/wdio.conf.ts`)이 모듈 최상위에서 그것을 부르고
전용 설정들은 전부 그것을 상속한다. 짝이 없으면 스펙 전부가 설정을 읽는
단계에서 죽는다. 러너는 이 경우 아무것도 돌리지 않고 `prerequisites-missing`
으로 적는다 — 환경이 없는 것과 회귀가 깨진 것은 다른 사실이다.

짝은 **핀 커밋과 같고 작업 트리가 깨끗해야** 한다. 조금이라도 다르면 결과를
믿을 수 없기 때문이다. 설정이 기본으로 보는 자리는 저장소 옆의
`naia-agent-worktrees` 인데, 배치에 따라 다르므로 자리를 알려 주고 돌린다.

```
NAIA_AGENT_WORKTREES_DIR=<짝 워크트리들이 있는 디렉터리> \
NAIA_E2E_ARTIFACTS_DIR=<쓰기 가능한 디렉터리> \
  node scripts/run-regression.mjs --machine=<명단의 이름> --tier=deterministic_ci
```

### 어느 기계가 무엇을 맡는가

`machines.json` 이 명단이다. 기계 이름과 능력, 그리고 지금 참여하는지
(`active`)를 적는다. 러너는 그것을 읽어 **등급마다 그 등급을 맡은 기계들끼리**
스펙을 나눈다. 등급을 합쳐 나누면 균등하지 않다 — 다섯 대가 맡는 등급과 두
대가 맡는 등급을 한 줄로 세우면, 두 대짜리 등급의 몫이 다섯 대에 흩어져
그중 셋은 돌릴 수 없는 것을 받는다.

기계마다 `--peers` 를 손으로 적지 않는 이유도 같다. 목록이 어긋나면 몫이
겹치거나 비는데, 각 기계는 "내 몫을 다 돌았다" 고 말하므로 기록만 보고는 알
수 없다.

배포 전에는 이 기록을 모아 본다.

```
node scripts/check-regression-complete.mjs --max-age-hours=24
```

아무도 맡지 않은 스펙이 있거나, 환경이 없어 건너뛴 것이 있거나, 실패한
기계가 있으면 통과하지 않는다. **건너뛴 것은 통과가 아니다** — 그것이
리눅스 음성 결함이 넉 달 산 이유였다.

### 이 기록이 믿을 만한 근거와 그 한계

기록에는 그 실행이 어느 코드·어느 스펙 목록에서 나왔는지가 함께 남는다
(`ranOn`: 인벤토리 해시, 커밋, 플랫폼, Node 판). 완결성 게이트는 그것을 보고
**다른 스펙 목록에서 돈 기록과 실행 시각이 미래인 기록을 판정에서 뺀다.**

**위조는 막지 못한다.** 기록은 저장소에 커밋되는 JSON 일 뿐이고, 커밋할 수
있는 사람이면 파일도 쓸 수 있다. 지문을 맞춰 적은 파일 하나로 "123개 전부
돌았다" 를 만들 수 있다 — 실제로 그렇게 되는 것을 확인했다. 코드로 구별할
방법은 없다.

여기서 막는 것은 **실수**다. 인벤토리가 바뀐 뒤의 낡은 기록, 다른 브랜치에서
돈 기록, 시계가 어긋난 기록. 이것들은 악의 없이도 생기고, 생기면 "전부
덮였다" 는 거짓 결론으로 이어진다. 신뢰의 경계는 저장소에 커밋할 수 있는
사람들이며, 그 경계 안에서 서로 정직하다는 전제 위에 이 프로세스가 선다.

기록은 커밋한다. 커밋하지 않으면 다른 기계가 그것을 볼 수 없고, 전체가
덮였는지 판단할 수 없다.
